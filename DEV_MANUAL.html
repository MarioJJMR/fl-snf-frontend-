01 — Panorama

Resumen del sistema

FL-SNF es un sistema de gestión de obras de construcción: administra usuarios, obras, proyectos, formularios y documentos, con notificaciones y un asistente tipo chatbot. Son dos repositorios independientes (no es un monorepo) que se despliegan como tres servicios separados en el mismo proyecto de Railway.

El frontend nunca habla directo con MySQL ni con los servicios externos: todo pasa por la API del backend. El frontend es un sitio multi-página sin build (cada pantalla es un .html independiente), por lo que su "despliegue" es literalmente publicar los archivos tal cual.

ServicioRepoRol

Backendfl-snf-backend-API REST (Express) — auth, obras, proyectos, formularios, documentos, notificaciones, chatbot, correo
Base de datos—Plugin MySQL de Railway, expuesto al backend vía MYSQL_PUBLIC_URL
02 — Backend

Arquitectura del backend

Stack y patrón

Node.js + Express 4, arquitectura por capas: routes → controllers → services → helpers. No usa ORM; las queries van directas con mysql2/promise.

fl-snf-backend-/ 
server.js          # entry point, middlewares, montaje de rutas
routes/             # auth, obras, usuarios, formularios, proyectos,
                    # documentos, correo, notificaciones, chatbot
controllers/        # uno por recurso (9 en total)
services/           # lógica de negocio + queries SQL
helpers/            # db.js, logger.js, mailer.js, s3.js, upload.js
middleware/         # auth.js (JWT), googleAuth.js
db/                 # schema.sql, migrate.js, seed.js, seed_ci.js
tests/              # Jest + Supertest
Nota

Los módulos notificaciones y chatbot (rutas, controllers y services) existen y están activos en el código, pero no aparecían en la documentación anterior. Trátalos como módulos de primera clase, no como features experimentales.

Base de datos

MySQL 8, base fl_snf_db. La conexión (helpers/db.js) se resuelve distinto según el entorno:

development / test

Variables individuales

Usa
DB_HOST, DB_USER, DB_PASSWORD, DB_NAME, DB_PORT
cualquier otro entorno (prod)

URL completa + SSL

Usa
MYSQL_PUBLIC_URL (parseada), conexión con SSL
Si falta
el proceso hace process.exit(1) al arrancar

Tablas principales (db/schema.sql): usuarios, obras, formularios (JSON), proyectos (JSON), documentos, password_reset_tokens, sesiones_revocadas (logout / revocación de JWT por jti) y notificaciones.

Autenticación

  • JWT (jsonwebtoken) verificado en middleware/auth.js — expone verifyToken, requireRole y requireObraAccess (control de acceso por obra, no solo por rol).
  • Revocación de sesión: al hacer logout se guarda el jti del token en sesiones_revocadas, y cada request valida contra esa tabla.
  • Roles: admin / usuario.
  • Google OAuth2 soportado en backend (middleware/googleAuth.js, valida el id_token contra GCP_CLIENT_ID), pero oculto en el frontend por el feature flag FEATURES.GOOGLE_LOGIN: false.

Tests

Jest + Supertest, en tests/ (incl. tests/services/). tests/smtp-real.test.js pega a un servicio real de correo y está excluido en CI. Mocks de helpers en helpers/__mocks__/.

03 — Frontend

Arquitectura del frontend

No es una SPA ni usa framework: es HTML/CSS/JS "vanilla", multi-página, sin bundler ni paso de build. Cada pantalla es un archivo .html independiente y la navegación entre ellas es window.location.href.

fl-snf-frontend-/ 
Inicio.html            # login
index.html              # portal de obra
admin_dashboard.html
proyectos.html
sondeo.html
reset-password.html
assets/
  css/styles.css
  js/
    config.js            # API_BASE, EmailJS, Google Client ID, feature flags
    api.js                # cliente fetch centralizado (JWT, timeout, 401 → login)
    main.js, admin_dashboard.js, forms-manager.js
Documentation/
  arquitectura.html, manual_admin.html, manual_usuario.html

Consumo de la API y estado

  • Cliente HTTP propio en assets/js/api.js: fetch nativo (no axios), agrega Authorization: Bearer <token>, timeout con AbortController (10s por defecto) y redirige a Inicio.html en un 401.
  • Sin librería de estado: la sesión vive en sessionStorage (clave usuarioActual, incluye el JWT).
  • Sin router de SPA: navegación entre archivos HTML reales.
Importante para cambiar de ambiente

No hay .env en el frontend. La URL del backend está hardcodeada en assets/js/config.js (detecta localhost vs producción por window.location.hostname). Apuntar el frontend a otro backend requiere editar este archivo y hacer commit, no cambiar una variable en Railway.

Tests

Jest con jest-environment-jsdom, en tests/ (api.test.js, forms-manager.test.js, main.test.js).

05 — Onboarding

Levantar el proyecto en local

Backend

  1. Clonar y configurar Copiar .env.example a .env y completar como mínimo DB_*, JWT_SECRET, FRONTEND_URL, credenciales del bucket y RESEND_* (ver tablas de arriba — el archivo de ejemplo no está completo).
  2. Base de datos Levantar MySQL 8 local, crear la base fl_snf_db y aplicar db/schema.sql.
  3. Instalar y poblar 
    npm install
node db/migrate.js
npm run seed
  4. Levantar el servidor 
    npm run dev   # nodemon, recarga en caliente
  5. Correr tests 
    npm test

Frontend

  1. Sin build No hay paso de compilación. Basta con servir la carpeta como archivos estáticos (p. ej. extensión Live Server, o npx serve).
  2. Apuntar al backend local assets/js/config.js ya usa http://localhost:3001/api cuando window.location.hostname === 'localhost' — solo asegúrate de correr el backend en el puerto 3001, o edita config.js si usas otro.
  3. Tests 
    npm test
06 — CI/CD

CI/CD y despliegue en Railway

Ambos repos tienen su propio workflow de GitHub Actions y su propio mecanismo de build de Railway — no comparten configuración.

Integración continua (GitHub Actions)

.github/workflows/ci.yml — backend

Dispara en

push/PR a main, develop, feature/**

Pasos
Levanta servicio MySQL 8 en contenedor → npm ci → aplica db/schema.sql → node db/migrate.js → node db/seed_ci.js → npm test (excluye smtp-real)
.github/workflows/ci.yml — frontend

Dispara en

push a main/develop/feature/**, PR solo contra main

Pasos
npm ci → npm test -- --ci --forceExit → npm run test:coverage → sube artefacto coverage/

Ninguno de los dos workflows hace deploy — el deploy a Railway ocurre por integración directa de Railway con el repo de GitHub (build-on-push), no como un paso de Actions.

Build y arranque en Railway

Backend · nixpacks.toml 
[phases.install]
cmds = ["npm ci --omit=dev"]

[start]
cmd = "npm run seed && node server.js"
Frontend · railpack.json 
{
  "$schema": "https://schema.railpack.com",
  "provider": "staticfile"
}
Verificar antes de tocar el arranque

El comando de start real en Railway (nixpacks.toml) ejecuta npm run seed, mientras que el script start de package.json ejecuta node db/migrate.js && node server.js. Son cosas distintas: uno pobla datos, el otro aplica migraciones. Antes de asumir cuál corre en producción, confirmarlo directamente en la configuración del servicio en Railway.

Servicios en Railway

Un mismo proyecto de Railway agrupa tres servicios: el sitio estático del frontend, la API del backend y el plugin de MySQL. El backend consume la base vía MYSQL_PUBLIC_URL, inyectada automáticamente por Railway al enlazar el plugin de MySQL al servicio backend. El resto de las variables (sección anterior) se configuran manualmente en la pestaña Variables del servicio backend.

Flujo de branches

Ambos repos usan main y develop, más ramas feature/** para trabajo en curso (CI corre en las tres). El deploy automático a producción típicamente está enlazado a main en la configuración de Railway — confirmarlo en el dashboard de cada servicio, ya que no queda declarado en ningún archivo del repo.

07 — Estado real vs. documentado

Deuda técnica y discrepancias

Hallazgos al comparar la documentación previa contra el código en el último commit de cada repo (2026-07-09). Se documentan tal cual están hoy; ninguno fue corregido en el código como parte de este manual.

Nombres de variables S3 desalineados

La documentación anterior listaba AWS_ACCESS_KEY_ID / S3_BUCKET_NAME. El código y .env.example reales usan BUCKET_NAME, BUCKET_ACCESS_KEY_ID, BUCKET_SECRET_ACCESS_KEY, BUCKET_REGION, BUCKET_ENDPOINT.

MYSQL_PUBLIC_URL no documentada

Es obligatoria en cualquier entorno que no sea development/test — su ausencia detiene el arranque del proceso — pero no aparecía en .env.example ni en la documentación previa del backend.

Scripts deploy* rotos en package.json

deploy, deploy:backend, deploy:frontend y deploy:check invocan bash deploy/deploy.sh, pero esa carpeta fue eliminada intencionalmente (ver RELEASE.md). Son scripts muertos hoy.

Módulos sin documentar

notificaciones y chatbot (rutas, controllers, services, y las variables RATE_LIMIT_*/RESEND_*/EXTRA_ORIGINS que trajeron) no estaban en ONBOARDING.md ni en arquitectura.html. Este manual ya los incorpora.

Arranque en Railway: seed vs. migrate

nixpacks.toml corre npm run seed en el start; package.json define start como node db/migrate.js && node server.js. Confirmar en Railway cuál es el comando de start efectivo del servicio antes de modificarlo.

Info de Railway centralizada en el repo equivocado

Las URLs de los tres servicios y las variables de entorno de producción vivían solo en Documentation/arquitectura.html del frontend, no en el backend. Este manual las junta en un solo lugar, fuera de ambos repos.

Sin escaneo de malware en la subida de archivos

Verificado por búsqueda exhaustiva en ambos repos (código y dependencias): no existe ningún mecanismo de escaneo antivirus/malware (ClamAV, VirusTotal u otro) en ningún punto del flujo de subida de documentos ni de "Logotipos institucionales". Los archivos van del navegador al backend o directo al bucket S3 sin ningún análisis de contenido malicioso.

Controles que sí existen (helpers/upload.js, services/documentosService.js):

  • Validación de MIME type por categoría y límite de 10 MB — solo en el flujo multipart (POST /api/documentos/:obraId).
  • Validación de magic bytes (firma binaria real) contra el mimetype declarado — misma limitación: solo en el flujo multipart. SVG y XML quedan explícitamente exentos de esta validación, y "Logotipos institucionales" acepta SVG.
  • El segundo flujo de subida, directo a S3 vía URL prefirmada (presigned-upload / confirm-upload), no pasa por ninguna de las dos validaciones anteriores: el backend nunca ve el contenido del archivo, solo confía en el mimetype y tamaño que el propio cliente reporta.
  • Mitigación parcial ya presente: la descarga siempre ocurre vía S3 presigned URL con Content-Disposition: attachment forzado, lo que evita que un archivo malicioso se renderice inline en el navegador al descargarlo.
Autorización de proyectos no aplicada

controllers/proyectosController.js (updateStatus, update, remove) solo bloquea la operación cuando el proyecto no pertenece a la obra del usuario — no cuando el usuario no es administrador. El texto de proyectos.html dice "Solo los administradores pueden cambiar el status", pero cualquier usuario de obra puede cambiar el status, editar o eliminar los proyectos de su propia obra.

08 — Referencia rápida

Guía rápida de operación

Antes de mergear a main

  • CI verde en ambos repos (backend corre contra MySQL real en el runner; frontend corre cobertura).
  • Si tocaste db/schema.sql, confirmar que db/migrate.js aplica el cambio de forma idempotente.
  • Si agregaste una variable de entorno nueva, agregarla también a .env.example y a la sección 04 de este manual — no solo al código.

Si el backend no arranca en Railway

  • Revisar que MYSQL_PUBLIC_URL esté enlazada (el plugin de MySQL debe estar conectado al servicio backend).
  • Revisar logs del servicio: un fallo de process.exit(1) temprano casi siempre es una variable de entorno faltante (sección 04).

Si el frontend no le pega al backend correcto

  • Es un problema de código, no de configuración de Railway: revisar assets/js/config.js y el valor de API_BASE para el hostname en cuestión.
